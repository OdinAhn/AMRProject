# AMR/AGV 관제 시스템 설계 문서

핵심 원칙: **전체 구조는 처음에 설계하고, 구현은 의존 순서대로 진행한다.** 프론트엔드는 백엔드 검증 후 구현하지만, 화면에 필요한 업무 흐름과 API는 처음부터 설계한다.

---

## 1. 시스템 개요와 확정된 조건

물류센터에서 작업 요청을 받아 로봇을 배정하고, 이동·적재·하역·충전을 관리하는 AMR/AGV 관제 시스템.

| 항목 | 현재 조건 |
|---|---|
| 백엔드 | Spring Boot |
| 기준 데이터베이스 | MySQL |
| 관리자 화면 | 지도·로봇·작업장·작업·장애·사용자 관리 |
| 작업자 화면 | 로봇 호출, 오는 중 표시, 로봇 보내기, 하역 완료, 재고 없음 |
| 개발 순서 | 백엔드 구현·검증 → 관리자 화면 → 작업자 화면 |
| 로봇 없는 개발 | 실제 통신 계약을 모사하는 가상 로봇 사용 |
| 설계 범위 | 기능, 데이터, 통신, 인프라, 보안, 장애 복구, 테스트, 배포 |
| Redis·Kafka·Kubernetes | 초기 설계에서 역할·필요성·도입 단계를 결정 |

### 미확정 항목 (임의로 확정된 것처럼 취급하지 않음)

| 미확정 항목 | 설계에 미치는 영향 |
|---|---|
| 완제품 로봇 연동 / 로봇 자체 개발 | 주행·센서·모터 제어를 우리가 개발하는지 |
| 로봇 제조사와 통신 규격 | MQTT, VDA 5050, 제조사 API 등 (18단계: VDA5050-over-MQTT 어댑터를 옵트인으로 구현해 검증 가능하게 함 — 그러나 실제 로봇 벤더 선정 자체와 그 벤더가 VDA5050을 지원하는지는 여전히 미정) |
| 초기·목표 로봇 대수 | 처리량, 배정 방식, 서버 용량 |
| 리프트·컨베이어 등 운반 장치 | 적재·하역 단계와 완료 확인 방식 |
| 기존 WMS/WCS 유무 | 재고·주문 정보의 기준 시스템 |
| 현장 서버 / 클라우드 환경 | 통신 단절 대응과 배포 구조 |
| 작업자 단말 | PC, 태블릿, 고정 키오스크 등 (12단계: 특정 단말을 정하지 않고, 반응형 웹 화면으로 구현해 브라우저가 있는 단말이면 형태와 무관하게 동작하도록 함 — 특정 단말 도입/구매 결정 자체는 여전히 미정) |

이 항목을 정하는 동안에도 작업·명령 모델과 가상 로봇 기반 개발은 진행할 수 있다.

1~13단계를 거친 뒤에도 위 7개 항목은 모두 그대로 미확정이다 — 각 단계에서 이 항목들과 부딪힌 지점은 항목을 임의로 확정하는 대신 범위를 좁히거나(예: 9단계 외부 연동은 벤더 중립 최소 계약만 구현) 기능을 보류하는(예: 리프트/컨베이어 미확정으로 `loads`/`load_transfer_events` 미구현, `docs/ERD.md` §4.8) 방식으로 처리했다. 각 단계별 구체적인 보류/축소 근거는 `docs/API.md`, `docs/ERD.md`, `docs/STATE_MACHINES.md`의 관련 절을 참고.

## 3. 서버와 로봇의 책임 분리

| 구성 | 담당 기능 |
|---|---|
| 중앙 백엔드 | 작업 접수, 로봇 배정, 경로·구역 사용 조정, 충전 계획, 이력 |
| 로봇 내부 | 위치 추정, 센서 처리, 경로 추종, 장애물 대응, 구동 장치 제어 |
| 안전 제어기 | 비상정지, 보호 정지 등 장비 안전 기능 |
| 외부 설비 | 자동문·엘리베이터·컨베이어 등의 동작과 인터록 |
| 관리자 화면 | 설정, 전체 관제, 작업 관리, 복구 |
| 작업자 화면 | 자기 작업장 업무 조회와 작업 확인 |

서버는 "이 작업장으로 이동하라"는 지시를 전달한다. 실제 주행은 로봇이 실행한다.

화면에서 요청한 정지와 실제 로봇의 안전 정지 상태는 별도로 관리한다. 서버의 정지 요청 성공을 실제 정지 완료로 표시해서는 안 된다.

## 5. 관리자와 작업자 업무 흐름

### 관리자: 운영 환경 설정

```
물류센터 등록
→ 지도 등록
→ 작업장·통로·충전소 정의
→ 로봇 등록·능력 설정
→ 설정 검증·활성화
→ 작업자에게 작업장 권한 부여
→ 운영 시작
```

### 작업자: 운반 업무

```
로봇 호출
→ 작업 생성
→ 로봇 배정
→ 로봇 오는 중
→ 출발 작업장 도착
→ 물품 적재
→ 작업자가 '로봇 보내기'
→ 목적지로 이동
→ 하역
→ 하역 완료 확인
→ 작업 완료
```

### 버튼 의미 (처음부터 고정)

| 행동 | 백엔드 의미 |
|---|---|
| 로봇 호출 | 운반 요청 생성 |
| 로봇 보내기 | 현재 단계의 적재 완료 확인 후 다음 이동 요청 |
| 하역 완료 | 물품 인계 확인 후 단계 완료 |
| 재고 없음 | 물류 예외 기록 및 진행 보류 |
| 작업 불가 | 사유 기록 및 운영자 처리 요청 |
| 호출 취소 | 현재 진행·적재 상태에 따라 취소 절차 시작 |

'재고 없음'을 누르면 재고 수량까지 수정하는지는 별도 결정 사항이다. 기존 WMS가 있다면 해당 시스템과 처리 계약을 맞춰야 한다.

## 6. 상태 모델과 데이터베이스

작업, 작업 단계, 로봇 명령을 분리한다.

```
작업: 물품을 A에서 B로 운반
 ├─ 단계: A로 이동
 │    └─ 명령: 해당 로봇에 이동 지시
 ├─ 단계: 적재 확인
 ├─ 단계: B로 이동
 │    └─ 명령: 해당 로봇에 이동 지시
 └─ 단계: 하역 확인
```

### 작업 상태

기본 상태:
```
QUEUED → ASSIGNED → RUNNING → SUCCEEDED
```

실행 중:
```
PAUSED
CANCEL_REQUESTED → CANCELED
RECOVERY_REQUIRED → 재개 또는 FAILED
```

### 명령 상태

```
PENDING → SENT → ACCEPTED → RUNNING → SUCCEEDED / FAILED
```

응답이 없어서 실제 실행 여부를 모르는 경우에는 별도의 불확실 상태를 둔다. 이를 바로 실패로 간주하고 다시 실행해서는 안 된다.

### 로봇 상태 (축 분리)

| 상태 축 | 예시 |
|---|---|
| 연결 | 온라인, 오래된 상태, 오프라인 |
| 운전 모드 | 자동, 수동, 점검 |
| 동작 | 대기, 이동, 도킹, 충전 |
| 안전 | 정상, 보호 정지, 비상정지 |
| 적재 | 비어 있음, 적재됨, 확인 불가 |
| 위치 | 정상 추정, 위치 상실, 확인 불가 |

### 주요 테이블

| 그룹 | 테이블 |
|---|---|
| 사용자 | users, roles, user_station_assignments |
| 시설 | sites, stations |
| 지도 | maps, map_versions, nodes, edges, zones |
| 로봇 | robots, robot_configurations, robot_state_snapshots |
| 작업 | tasks, task_steps, task_assignments, task_events |
| 명령 | robot_commands, command_events |
| 자원 | resource_reservations, charging_sessions |
| 물품 | loads, load_transfer_events |
| 이벤트 | outbox_events, inbox_messages |
| 운영 | alarms, alarm_events, audit_logs |

관리자 설정과 로봇이 실제 보고한 값은 분리한다. 설정에는 요청 버전과 실제 적용 버전을 기록한다.

## 7. 기술 스택과 역할

확정한 기술과 제안 기술을 구분한다.

| 영역 | 기술·방식 | 상태 |
|---|---|---|
| 백엔드 | Spring Boot | 확정 |
| 기준 저장소 | MySQL | 확정 |
| ORM | Spring Data JPA | 제안 |
| 인증·권한 | Spring Security | 제안 |
| DB 마이그레이션 | Flyway | 제안 |
| API 문서 | OpenAPI | 제안 |
| 조회 캐시 | Redis | 도입 범위 결정 필요 |
| 내부 이벤트 | Kafka | 도입 규모·시점 결정 필요 |
| 로봇 통신 | MQTT 또는 제조사 API | 장비 확인 필요 |
| 화면 실시간 상태 | SSE 우선 검토, 양방향 요구 시 WebSocket | 제안 |
| 지도 파일 | 파일 저장소 또는 객체 저장소 | 배포 환경에 따라 결정 |
| 컨테이너 | Docker | 제안 |
| 배포·복구 | Kubernetes | 운영 환경·고가용성 요구에 따라 결정 |
| 관측 | Actuator/Micrometer, Prometheus·Grafana 등 | 35단계: Actuator + Micrometer Prometheus 레지스트리와 업무 게이지까지 구현(`docs/DEPLOYMENT.md` §4). Prometheus·Grafana 서버 구성과 경보 규칙은 미정 |
| 로그·추적 | 중앙 로그, OpenTelemetry 등 | 규모에 따라 단계 적용 |
| 통합 테스트 | JUnit, Spring Boot Test, Testcontainers | 제안 |
| CI/CD | 사용하는 저장소의 자동 빌드·배포 도구 | 환경 확인 필요 |

특정 버전과 호환성은 프로젝트 생성 전에 확인해 고정한다.

### Redis·Kafka·Kubernetes의 경계

- **MySQL**: 작업·명령·배정·설정의 기준 데이터.
- **Redis**: 유실돼도 복구 가능한 조회 캐시.
- **Kafka**: 내부 이벤트 전달과 소비자 분리·재처리.
- **로봇 브로커/Gateway**: 실제 장비 연결과 명령 전달.
- **Kubernetes**: 애플리케이션 배포와 프로세스 복구.

Kafka를 사용해도 물리 동작의 중복 실행은 자동으로 해결되지 않는다. Kubernetes를 사용해도 작업 복구 로직은 별도로 필요하다.

## 8. 애플리케이션과 배포 구조

처음부터 기능마다 마이크로서비스를 만들지는 않는다. 하나의 코드베이스에서 모듈을 분리하고, 필요에 따라 API·워커·Gateway를 별도 실행한다.

```
관리자 / 작업자 화면
        ↓
Spring Boot API
        ├─ MySQL
        ├─ Redis 조회 캐시
        └─ 작업 + Outbox 저장
                    ↓
              이벤트 발행
                    ↓
                  Kafka
           ┌────────┼─────────┐
        작업 처리   상태 처리   로봇 Gateway
                                  ↕
                           장비 통신 / MQTT
                                  ↕
                                 로봇
```

Kafka를 도입하는 구성에서도 실제 명령 송신은 저장된 명령 상태와 유효성을 확인한 뒤 수행한다.

### 배포 설계에 포함할 내용

- 현장 내부에서 유지해야 할 기능과 외부 연결 기능.
- API의 수평 확장 방식.

## 9. 처음부터 구현에 반영해야 하는 신뢰성 규칙

이 항목들은 운영 직전에 덧붙이면 구조 변경이 커지므로, 첫 작업 흐름부터 반영한다.

| 문제 | 설계·구현 |
|---|---|
| 호출 버튼 중복 클릭 | 멱등성 키와 DB 유일성 제약 |
| 같은 로봇에 동시 배정 | 트랜잭션과 배정 충돌 검출 |
| DB 저장 후 이벤트 발행 실패 | Transactional Outbox |
| 이벤트 중복 수신 | 소비자 중복 제거와 상태 버전 검사 |
| 늦게 도착한 완료 응답 | 작업·명령 ID와 전이 조건 검사 |
| 서버 재시작 | 저장 상태와 실제 로봇 상태 대조 |
| 명령 응답 유실 | 실행 여부 확인 후 복구 판단 |
| 이벤트 재생 | 과거 물리 명령의 재실행 차단 |
| 로봇 통신 단절 | 점유 구역 유지, 신규 배정 제한 |
| 여러 Gateway 실행 | 로봇별 제어 소유권과 이전 실행자 차단 |

적재·하역 중 통신이 끊겼다면 무조건 재시도하지 않는다. 물품과 장비의 실제 상태를 먼저 확인한다.

## 10. API와 프론트 계약 (백엔드 개발 초기에 정의)

### 대표 API

| 대상 | 기능 |
|---|---|
| 관리자 | 지도·작업장·로봇 등록 및 설정 |
| 관리자 | 지도·설정 검증, 활성화, 적용 상태 조회 |
| 관리자 | 전체 작업·알림 조회, 취소·복구 |

| 외부 시스템 | 작업 접수, 결과 조회·회신 |

- 초기 상태 스냅샷.

- 오래된 로봇 상태 표시.
- 여러 서버 인스턴스에 연결된 사용자에게 이벤트 전달.
- 위치 업데이트가 업무 완료 이벤트를 밀어내지 않도록 처리.

## 12. 프론트엔드 시작 전 백엔드 완료 기준

다음 조건을 충족하면 프론트엔드 개발로 넘어간다.

- API만으로 호출부터 운반 완료까지 실행할 수 있다.
- 관리자 설정과 작업자 권한이 검증된다.
- 중복 클릭·중복 메시지로 작업이나 동작이 중복되지 않는다.
- 취소·재고 없음·적재 실패의 처리 결과가 정의되어 있다.
- 다중 로봇 배정·통로·충전 경쟁을 검증했다.
- 서버 재시작과 통신 단절 후 상태를 대조할 수 있다.
- 화면용 조회·실시간 이벤트·오류 계약이 문서화되어 있다.
- 로그로 작업과 명령을 끝까지 추적할 수 있다.
- 배포·백업·복원 절차를 검증했다.

실제 장비가 없다면 시뮬레이터 기반 백엔드 검증 완료로 표시하고, 실기 검증 항목을 남긴다. 프론트엔드 연동 중 작은 API 조정은 가능하지만, 핵심 작업 모델이나 인프라 책임을 그때 다시 설계하지 않는 것이 목표다.
