# 13단계 — 현장 검증 절차서

`docs/DESIGN.md` §11의 13단계("제한 구역·단일 로봇부터 단계 확대", 완료 기준 "현장 운반·복구 절차 검증")는 실제 로봇과 실제 현장이 있어야 하는 운영 활동이라 이 저장소의 소프트웨어 구현 범위에 포함하지 않기로 확인했다(1~12단계로 프로젝트 소프트웨어 구현은 완료). 이 문서는 실제 현장·로봇이 준비됐을 때 따를 절차서다 — 코드 변경 없이 문서만 정리한다.

---

## 1. 시작 전 확정돼야 하는 것 (docs/DESIGN.md §1 미확정 항목)

아래가 정해지지 않으면 현장 검증을 시작할 수 없다. 소프트웨어는 준비돼 있지만 이 항목들은 조달/현장 결정이라 코드로 대신할 수 없다.

| 항목 | 현재 상태 |
|---|---|
| 실제 로봇 벤더 | 미정 — `RobotGateway` 포트는 준비돼 있고, VDA5050을 지원하는 벤더라면 18단계 `MqttRobotGateway`를 시작점으로 쓸 수 있다. 지원하지 않으면 같은 포트의 새 어댑터가 필요하다 |
| 로봇 통신 규격이 VDA5050인지 | 18단계 어댑터는 축소 구현(단일 노드 order, 최소 state 필드)이라 실제 로봇의 전체 스펙 준수 여부를 먼저 확인해야 한다 |
| **동기식-타임아웃 설계의 한계** | 18단계 `MqttRobotGateway`는 `RobotGateway.dispatch()`의 동기 계약을 맞추려 3초만 기다린다 — 실제 로봇의 이동 시간은 훨씬 길다. 현장 검증 전에 **반드시** `TaskService`의 명령 완료 처리를 비동기로 재설계해야 한다(별도 스테이지 필요, 이 문서 §5 참고) |
| 지도 파일 형식/좌표계 | 미정 — 6단계에서 노드/통로/구역을 API로 직접 입력하는 임시 저작 도구로 대체했다. 실제 시설 도면을 이 좌표계로 옮기는 작업이 필요 |
| 리프트/컨베이어 등 연동 설비 | 미정 — 있다면 적재/하역 확인 방식(`loads`/`load_transfer_events`, 미구현)을 먼저 설계해야 한다 |
| 기존 WMS/WCS 연동 대상 | 미정 — 9단계 최소 접수 계약(`/api/external/tasks`)만 있고 실제 시스템 연동은 안 됨 |
| 현장 서버/클라우드 배포 구조 | 미정 — 지금까지는 로컬 Docker Compose로만 검증 |
| 작업자 단말 | 반응형 웹이라 기기 자체는 안 가리지만, 실제 현장에 배치할 단말(PC/태블릿/키오스크) 조달은 미정 |
| 네트워크(로봇 Wi-Fi 등) | 현장의 실제 무선 커버리지·지연·단절 패턴 확인 필요 — 8단계 장애 복구 로직이 가정한 것과 실제가 다를 수 있다 |

---

> 43단계: 현장에 가기 전, `tools/virtual-robot/`의 VDA 5050 가상 로봇으로 서버의 MQTT 모드 전체 흐름(운반·충전·비상정지·통신 두절)을 먼저 확인할 수 있다. 가상 로봇은 서버 구현에 맞춘 것이라 실제 로봇 제조사의 VDA 5050 해석(노드 id 체계, startPause 처리, 전체 경로 주문 필요 여부)은 여기서 따로 확인해야 한다.

## 2. 검증 원칙

- **제한 구역·단일 로봇부터 시작**한다(DESIGN.md §11). 넓히기 전에 각 단계의 종료 기준을 통과해야 한다.
- **물리적 안전이 항상 소프트웨어 판단보다 우선**한다 — `safety_state`(STATE_MACHINES.md §4.4)는 로봇이 보고하는 값을 그대로 신뢰하고, 화면의 "정지 요청" 성공과 실제 정지 여부를 동일시하지 않는다(DESIGN.md §3).
- **적재 중 통신 단절 시 무조건 재시도하지 않는다** — 물품과 장비의 실제 상태를 먼저 확인한다(DESIGN.md §9). 8단계 복구 정책(`RECOVERY_REQUIRED` + `recover`)이 이 원칙을 구현한 것이므로, 현장에서도 자동 재시도로 우회하지 않는다.
- **모든 이상 상황은 알람으로 남긴다** — 14단계 알람(`GET /api/admin/alarms`)과 15단계 실시간 스트림(`GET /api/events/stream`)으로 실시간 관찰하고, 각 단계 종료 후 알람 이력을 리뷰한다.
- **각 단계 확대는 운영 책임자 승인 후 진행**한다 — 되돌릴 수 있는 실패(소프트웨어 롤백)와 되돌릴 수 없는 실패(물리적 사고)를 구분해 판단한다.

## 3. 단계별 절차

### 0단계 — 사전 점검 (로봇 없이)

- §1의 확정 항목이 모두 정리됐는지 확인.
- 실제 현장 지도를 6단계 도구로 입력하고 `validate`/`activate`.
- 작업장(station) 등록 및 `map-binding` 완료.
- 관리자 계정으로 로그인해 화면(11단계)에서 지도·작업장·로봇 등록 화면이 정상 동작하는지 확인.

### 1단계 — 제한 구역, 로봇 1대, 사람 감독 하 저속 운영

- **진입 조건**: §1 전부 확정, 로봇 1대가 `RobotGateway` 어댑터로 실제 통신 확인됨(간단한 이동 명령 1건이 왕복 성공).
- **시나리오**: 정상 운반 1건(호출→배정→적재 확인→이동→하역 확인) 전 과정을 감독자 입회 하에 수행.
- **관찰**: `GET /api/admin/robots/{id}/state`로 실시간 상태, `GET /api/admin/alarms`로 이상 발생 여부, 작업자 화면(12단계)에서 버튼 흐름이 실제 로봇 동작과 일치하는지.
- **종료 기준**: 정상 흐름 10회 이상 반복해 실패 없음. 의도적 취소(호출 취소, 작업 불가) 각 1회 이상 시도해 8단계 설계대로 처리되는지 확인.
- **롤백 기준**: 로봇이 예상치 못하게 정지/이동하거나, 안전 센서가 오작동하거나, 소프트웨어 상태와 로봇 실제 상태가 어긋나는 사례가 1건이라도 있으면 중단하고 원인 분석 후 재시도.

### 2단계 — 같은 구역, 통신/전원 장애 주입

- **진입 조건**: 1단계 종료 기준 통과.
- **시나리오**: 이동 중 로봇 Wi-Fi를 의도적으로 끊거나 로봇을 강제 정지시켜 `RECOVERY_REQUIRED` 전이와 관리자 `recover`(RESUME/FAIL) 처리를 실제로 검증. 저배터리 상태를 만들어 자동 충전 배정(7단계)이 현실적인 시간 안에 이뤄지는지 확인.
- **관찰**: 14단계 `ROBOT_COMM_LOST` 알람이 실제로 발생·해소되는지, 8단계가 가정한 "적재 중이면 즉시 취소하지 않는다" 원칙이 실제로 지켜지는지.
- **종료 기준**: 통신 단절 3회 이상 시나리오에서 물품 중복 배송/중복 동작 없이 복구되거나 운영자 개입으로 안전하게 종료됨.
- **롤백 기준**: 중복 물리 동작(같은 물품을 두 번 옮기려 시도 등)이 한 번이라도 발생하면 중단.

### 3단계 — 같은 구역, 로봇 2대 이상 (다중 로봇 경쟁)

- **진입 조건**: 2단계 종료 기준 통과.
- **시나리오**: 같은 station에 여러 로봇이 몰리는 경쟁 상황, 자동 배정(`POST /api/admin/sites/{siteId}/dispatch`, 7단계)이 실제로 충돌 없이 동작하는지.
- **관찰**: `resource_reservations` 기반 station 점유가 실제 로봇 동선과 일치하는지(7단계는 station 단위 예약만 하고 통로/구역 예약은 로봇 위치 추적이 없어 미구현임을 상기 — 통로에서의 물리적 충돌 가능성을 현장에서 별도로 관리해야 한다).
- **종료 기준**: 로봇 2대 기준 정상 운반 20회 이상, 충돌/교착 없음.
- **롤백 기준**: 통로 상 물리적 충돌 위험이 확인되면 즉시 중단 — 소프트웨어가 통로 예약을 하지 않는다는 §1 한계를 현장 레이아웃/운영 규칙으로 보완해야 한다.

### 4단계 — 구역 확대, 정상 운영 규모로 전환

- **진입 조건**: 3단계 종료 기준 통과, 운영 책임자 승인.
- **시나리오**: 목표 구역 전체로 확대, 정상 근무조 운영자가(감독자 없이) 작업자 화면만으로 하루 이상 운영.
- **종료 기준**: 사전에 합의한 운영 목표(처리량, 알람 대응 시간 등)를 충족.

---

## 4. 각 단계 공통 산출물

- 알람 이력 스냅샷(`GET /api/admin/alarms`, 기간 내 전체).
- 취소/복구(`recover`) 발생 건수와 처리 결과.
- 발견된 소프트웨어 결함 목록과 재현 절차(가능하면 시뮬레이터로 재현해 통합 테스트로 남긴다 — 4단계 시뮬레이터가 여전히 회귀 테스트의 기준이다).
- 다음 단계 진입 승인 기록(승인자, 일시, 조건 충족 여부).

---

## 5. 이 문서가 시작 전 요구하는 후속 작업

- **비동기 명령 처리 재설계** — `docs/API.md` §7에 이미 명시된 대로, 18단계 MQTT 어댑터의 3초 동기 대기는 데모용이지 실제 로봇에 쓸 수 없다. `TaskService`가 명령을 보낸 뒤 나중에 별도로 도착하는 완료 신호를 받아 다음 단계로 진행하는 구조로 바꿔야 한다 — `RobotGateway` 인터페이스 계약 자체를 바꾸는 큰 작업이라 별도 스테이지로 계획한다.
- **통로/구역 단위 자원 예약** — 로봇 위치 추적이 생기면 7단계의 "station만 예약" 한계를 넘어 실제 통로 충돌 방지가 가능해진다.
- **`loads`/`load_transfer_events` 구현 여부 재검토** — 실제 리프트/컨베이어 연동이 결정되면 8단계에서 보류한 물품 단위 추적을 다시 검토한다.
